# gobrowser 通用 Web 渲染运行时 · 架构方案（v0.3）

> 目标：把 Electron 当"哑终端"。业务层用 Go，用户双击 Go 程序 → 它在统一目录里找到共享的 Electron 运行时 → 拉起一个属于自己实例的窗口 → 渲染 Go 后端提供的页面，并通过本地 HTTP API 控制窗口。
> 多份运行时可在同一台机器上被多个 Go 程序共用；同时多个 Go 程序各自独立进程、独立数据。

---

## 0. 已确认的约束

| # | 约束 | 含义 |
|---|---|---|
| 1 | **多平台**：Windows + Linux，覆盖你手上的加固包 | win-x64 / win-ia32 / linux-x64 / linux-arm64 / linux-loong64 / linux-mips64el / linux-sw64 |
| 2 | **运行时共用** | 统一目录下已有一份运行时，其他 Go 程序**不再自带** |
| 3 | **Go 程序是入口** | 用户双击 Go 程序，它负责找到并拉起运行时 |
| 4 | **并发隔离** | 多个 Go 程序同时运行，各自身份、各自数据，互不打扰 |
| 5 | **UI 只由后端提供** | `entry` 只有 URL，不支持纯静态页面 |
| 6 | **事件先 HTTP 回调，预留 WS** | 事件层做成 adapter |

### 一条重要的推论（改掉了 v0.2 的设计）

既然**用户双击的就是 Go 程序**，那么"程序名 + 图标"天然由 **Go 程序自己的 exe 承载**（Go 编译时就能写入 icon / version info / 公司名）。
外壳 `gobrowser.exe` 只是一个**看不见的渲染子进程**。

**所以共享模式不需要额外的 launcher，也不需要给每个应用复制一份 180MB 的运行时。**
v0.2 里"独立形态 = 每应用一份副本"的设计被推翻；改为：

| 模式 | 何时用 | 磁盘 |
|---|---|---|
| **shared（默认）** | 一个客户端装了多个 Go 产品；或运行时想统一升级 | 仅一份（约 180 MB） |
| standalone（可选保留） | 交付给客户时要求"进程名也必须是自己的"，或要完全离线独立分发 | 每个产品一份 |

## 1. 运行时分发模型

**一个"统一目录"里放运行时，多个 Go 程序和它同级：**

```
D:\Apps\                          ← 统一目录（部署位置随意，用户自己定）
├── runtime\                      ← 共用的一份，整份 Electron 加固 dist
│   ├── gobrowser.exe  electron.sign  lic\  *.dll  *.pak  locales\
│   └── resources\app.asar
├── ReportApp.exe                 ← Go 产品 A（自带图标/名字/版本/公司名）
├── ReportApp.app.json            ← 与 exe 同名：多个产品放一起不会互相覆盖
├── OtherApp.exe                  ← Go 产品 B（同样只找同级 runtime）
└── OtherApp.app.json
```

- 一台机器、一个统一目录 → **只有一份运行时**，N 个 Go 程序共用。
- 不写注册表、不装 Program Files、不需要管理员权限，整个目录可以直接打包拷走。
- 某个产品想完全自包含（绿色分发）：把它自己的 `runtime\` 放在它旁边（同级优先命中），见 §2。

## 2. 运行时发现与版本选择

### 2.0 运行时从哪来（SDK 的决策顺序）

| 顺序 | 来源 | 触发条件 |
|---|---|---|
| 1 | 同级 `..\runtime\` → `.\runtime\` | 总是先找本地 |
| 2 | exe 尾部载荷（`-single` 形态） | 有载荷就解压到用户缓存，按摘要复用 |
| 3 | **自动下载** | 开发态（`go run`）默认开；生产包需显式 `GOBROWSER_AUTO_FETCH=1` |
| 4 | 报错退出（码 2，写日志 + 原生错误框） | 以上都拿不到 |

第 3 条的边界（重要）：**`go build` 出来的程序不会自己联网**。判断依据是 `debug.ReadBuildInfo().Main.Path`——
`go run` 编译出来是 `command-line-arguments`，正常构建是模块路径，所以生产环境行为完全不变。

下载走 `internal/runtimefetch`：读内嵌清单（版本 / 平台 / URL / size / sha256）→ 缓存到
`%LOCALAPPDATA%\gobrowser\runtimes\<版本>-<平台>\` → 校验通过才解压 → 同一台机器只下一次。
镜像与离线由环境变量控制：`GOBROWSER_RUNTIME_BASE`（换源）、`GOBROWSER_RUNTIME_DIR`（读本地 zip）、
`GOBROWSER_RUNTIME_CACHE`（换缓存）、`GOBROWSER_AUTO_FETCH=0`（关闭）。

### 2.1 同级目录的查找顺序

Go 侧按顺序找，第一个命中的胜出：

**同级目录之外不查注册表、不查 Program Files**（环境变量只用于自动下载那一路的镜像/缓存配置，见 2.0）。

按顺序看两个位置：

| 顺序 | 路径 | 场景 |
|---|---|---|
| 1 | `<Go程序所在目录>\..\runtime\` | **与程序同级 —— 主用法（统一目录共用）** |
| 2 | `<Go程序所在目录>\runtime\` | 程序内部自带（便携/自包含，优先级低，兜底） |

> 判定用"能不能正常渲染"的最小文件集；`runtime\` 里只要缺一项就当作无效，继续找下一处，全都无效就报错。

命中判定的最小条件（缺任意一项都算"运行时无效"）：

```
runtime\
├── gobrowser.exe          ← 必须有
├── electron.sign         ← 必须有
├── lic\                  ← 必须有
├── resources\app.asar    ← 必须有（底座代码）
├── version               ← 读它拿版本号（可空，仅用于日志）
└── *.dll  *.pak  locales\ …
```

**找不到 / 不完整时的行为**（明确、可诊断，不白屏）：

```
[gobrowser] 未找到可用运行时
  期望路径: D:\Apps\runtime\gobrowser.exe
  也尝试过: D:\Apps\ReportApp\runtime\gobrowser.exe
  缺失项  : gobrowser.exe
  处理建议: 把 runtime 目录放到程序同级目录（与本程序在同一父目录下）
```

- 写到 **stderr**，退出码 `2`，不弹窗、不继续启动。
- 若 Go 程序是 `-H windowsgui`（无控制台），stderr 看不到 → 建议同时追加一行到 `%LOCALAPPDATA%\<appId>\logs\shell.log`（**这条待你确认要不要**）。

## 3. 进程模型与启动流程

```
MyApp.exe（Go，用户双击的就是它，进程名/图标都是自己的）
  │ ① 读同目录 <程序名>.app.json（找不到再退回 app.json）→ 按 §2 找到运行时 + 校验完整性（electron.sign / lic / resources\app.asar）
  │ ② Go 自己监听 127.0.0.1:0（提供页面 + 接收事件回调）
  │ ③ spawn
  └─> <同级 runtime>\gobrowser.exe --app="…\ReportApp.app.json" --entry="http://127.0.0.1:<port>/" --events="http://127.0.0.1:<port>/_shell/events"
        │  stdout 首行：{"event":"ready","port":51234,"token":"…","pid":1234}
        │  ④ Go 读到握手 → 用 HTTP API 开窗口 / 或让外壳按 app.json 自动开
        └─> Chromium 子进程（renderer/gpu/utility）
```

| 机制 | 方案 | 理由 |
|---|---|---|
| 端口 | 外壳 `listen(0)`；Go 后端同样用 0 | 多程序并发绝不撞端口 |
| 握手 | **stdout 首行 JSON**（含 port + token） | Go 只需读一行，零轮询、零临时文件 |
| 鉴权 | 每次启动随机 token → `Authorization: Bearer` | 防本机其它进程/网页乱调 |
| 生命周期 | 外壳跟随父进程（Win: Job Object `KILL_ON_JOB_CLOSE`；Linux: `PR_SET_PDEATHSIG`） | Go 崩了不留僵尸窗口 |
| 单实例 | 按 `appId` 加锁（Win 命名 Mutex / Linux lock 文件） | 同一程序重复双击激活已有窗口 |

> 注意：共享的是**磁盘上的二进制**，不是进程。3 个 Go 程序 = 3 个外壳进程 = 3 套 Chromium。见 §5 的内存账。

## 4. 品牌矩阵（共享模式下"尽量都要"能到哪一步）

| 用户能看到的位置 | 共享模式能做到吗 | 靠什么 |
|---|---|---|
| 用户双击的那个图标 / 文件名 | ✅ | 就是 Go 程序的 exe（Go 编译时写入 icon + version info） |
| 右键属性里的产品名、公司、版本 | ✅ | 同上 |
| 窗口标题 | ✅ | `app.json` → `BrowserWindow.title` / `app.setName` |
| 窗口 / 任务栏按钮图标 | ✅ | `BrowserWindow({ icon })` |
| 托盘图标与菜单 | ✅ | `Tray` |
| 通知里的来源名称与图标 | ✅ | `app.setAppUserModelId(appId)` + 为该 AUMID 注册开始菜单快捷方式 |
| 任务栏分组 | ✅ | 按 `appId` 分 AUMID |
| 安装包名称与图标 | ✅ | 各产品自己的安装包 |
| 任务管理器里的**主**进程 | ✅ | 就是 Go 程序 |
| 任务管理器里的**子**进程 | ❌ 显示 `gobrowser.exe` | 只有运维/开发会看到；要连这个都改，才需要 standalone |

**结论**：共享模式已经覆盖了终端用户能感知到的全部品牌位置，
只有"任务管理器里那个渲染子进程的名字"改不了 —— 这是共享二进制的唯一代价。

## 5. 隔离与成本

### 5.1 数据隔离矩阵（多程序并发的核心）

| 资源 | 隔离方式 | 不做会怎样 |
|---|---|---|
| 端口 | 两侧都 `listen(0)` | 第二个程序起不来 |
| Cookie / localStorage / IndexedDB | `app.setPath('userData', appData/<appId>)` | ⚠️ Electron 默认用 `package.json.name`，同名即串数据（已实测） |
| 磁盘缓存 / GPU 缓存 | 跟随 userData 自动隔离 | 缓存互相污染 |
| 日志 | `%LOCALAPPDATA%\<appId>\logs` | 排查时日志混在一起 |
| 临时文件 / 下载目录 | `app.setPath('temp', …)` / `setDownloadPath` | 文件互相覆盖 |
| 单实例锁 | 按 `appId` 命名 | 重复双击开两窗 |
| 任务栏分组 / 通知 | `app.setAppUserModelId(appId)` | 两个程序被合并成一组 |
| 全局快捷键 | ⚠️ **进程间冲突**，同一组合键只能一个程序注册 | 后启动的注册失败 → 按 appId 分配或可配置 |

`appId` 是整套隔离的锚点（目录名 / 锁名 / AUMID / 通知分组），`app.json` 里强制必填且全局唯一。

### 5.2 磁盘 vs 内存（别把"共用"理解错）

| 项 | 共享模式 | 说明 |
|---|---|---|
| 磁盘 | **一份 180 MB**（N 个产品也只占一份） | 这就是共享的收益 |
| 内存 | **每个 Go 程序一套**：单窗 120–180 MB，多开 3 个产品 400–600 MB | 共享二进制**不省内存** |

如果将来内存是瓶颈，可以做"多 app 单进程壳池"（一个外壳托管多个应用的窗口），但会牺牲隔离（一崩全崩），不建议放进 MVP。

```
【统一目录】D:\Apps\                    ← 位置随意，绿色部署，可整目录拷走

【运行时数据】（始终与程序目录分离，按 appId 隔离）

       %LOCALAPPDATA%\<appId>\logs\  外壳日志 / 崩溃转储
Linux: ~/.config/<appId>\  ~/.cache/<appId>\  ~/.local/share/<appId>/logs\
```

## 7. `<程序名>.app.json`

**为什么不是固定的 `app.json`**：一个统一目录里可能放多个产品，共用一个 `app.json` 会互相覆盖（后放进去的赢），而每个程序双击时都会读它 → 读到别人的 appId、别人的窗口参数，数据目录也会串。所以约定**配置文件名跟着 exe 走**。

查找顺序（SDK 自动做，开发者不用管）：

| 顺序 | 位置 | 场景 |
|---|---|---|
| 1 | `<程序名>.app.json` | **新约定** —— 多产品共用一个目录 |
| 2 | `app.json` | 单产品目录的旧约定，兼容保留 |

> 源码目录里仍然叫 `app.json`（好写）；`tools/build` 出包时会落成 `<程序名>.app.json`。

```jsonc
{
  "appId": "com.acme.report",              // 隔离锚点，全局唯一
  "name": "报表中心",
  "version": "1.2.0",

  "entry": {
    "url": "http://127.0.0.1:0/",          // 0 = 用 Go 实际监听的端口，由 Go 启动时替换
    "waitFor": { "timeoutMs": 15000, "intervalMs": 200 },
    "errorPage": true
  },

  "events": "http://127.0.0.1:0/_shell/events",

  "window": {
    "width": 1280, "height": 800, "minWidth": 900, "minHeight": 600,
    "frame": false, "center": true, "titleBarStyle": "hidden",
    "alwaysOnTop": false, "icon": "icon.png"
  },

  "tray": { "enabled": false, "icon": "icon.png", "tooltip": "报表中心", "menu": [] },

  "security": {
    "allowNavigation": ["http://127.0.0.1:*"],
    "devTools": false,
    "fileSignCheck": [],
    "encryptStorage": true,
    "injectBridge": true
  },

  "singleInstance": true,
  "closeToTray": false,
  "gpu": "auto",
  "shortcuts": { "toggleWindow": "Ctrl+Alt+F1" }
}
```

> `url` 里的端口由 Go 在启动时用实际端口替换（或作为 `--entries` 参数传入），避免把端口写死在文件里。

## 8. 启动时序（不支持纯静态 → 必须设计）

```
Go 启动 → 监听端口 → spawn 外壳
  → 外壳显示内置 splash（在 asar 内，不算静态应用）
  → 轮询 entry.url 直到 200（200ms / 最长 15s）
       ├─ 成功 → 导航
       └─ 超时 → 内置错误页：URL + 重试 + 日志路径 + 退出
  → 运行中后端挂了：事件回调连续失败 N 次 → 半透明遮罩"连接已断开" + 自动重连
```

## 9. 三个接口面

### 9.1 控制面（Go → 外壳）：本地 HTTP-RPC

`POST` + `Authorization: Bearer <token>`，返回 `{"ok":true,"data":…}` / `{"ok":false,"error":{…}}`。

| 分组 | 端点 |
|---|---|
| 元信息 | `GET /v1/health` · `GET /v1/info` · `POST /v1/shutdown` |
| 窗口 | `POST /v1/windows` · `…/{id}/close` `navigate` `maximize` `unmaximize` `minimize` `restore` `show` `hide` `focus` `center` |
| 窗口属性 | `…/bounds`(GET/PUT) · `title` · `always-on-top` · `opacity` · `resizable` · `fullscreen` |
| 托盘 | `POST /v1/tray` · `…/menu` · `…/destroy` |
| 对话框 | `POST /v1/dialog/open` `save` `message` |
| 系统 | `POST /v1/notify` · `clipboard` · `shortcut` · `open-external` |
| 屏幕 | `GET /v1/displays` · `/v1/cursor` |

MVP = 窗口 + 托盘。

### 9.2 事件面（外壳 → Go）：只保留最小集，不做 WS

**结论：当前业务没有消费事件的场景，所以不投入 WS，只保留几种"确实可能要用"的事件。**

```json
{ "event": "window.closed", "appId": "com.acme.report", "windowId": "main", "ts": 1730000000, "payload": {} }
```

| 保留 | 为什么 |
|---|---|
| `window.closed` / `window.maximized` / `window.restored` / `window.minimized` | 低频，业务偶尔要同步状态 |
| `tray.click` / `menu.click` | 托盘菜单要触发业务逻辑时的唯一入口 |
| `second-instance` | 二次双击要激活已有窗口 |
| `app.ready` / `app.before-quit` | 排查用 |

已删除：`window.focus` / `window.blur` / `resize` / `moved` —— 高频且没有消费方，只会把日志刷满。

**替代方案（推荐优先用）**：托盘菜单支持内置动作，不需要 Go 参与就不会产生事件往返：

```json
"tray": { "menu": [
  { "id": "show", "label": "显示主窗口", "action": "show" },
  { "id": "hide", "label": "隐藏",       "action": "hide" },
  { "id": "site", "label": "打开官网",   "action": "open:https://example.com" },
  { "type": "separator" },
  { "id": "quit", "label": "退出",       "action": "quit" }
]}
```

只有"点菜单要跑业务代码"这种才需要事件；那种情况本来也可以让页面自己处理（`window.webshell.on`）。

### 9.3 页面直连（省掉两跳）

外壳给所有窗口注入 preload：

```js
window.webshell = {
  window: { minimize, maximize, close, toggleMaximize, setTitle, isMaximized },
  app:    { version, platform, reload, quit },
  on:     (event, handler) => {}
}
```

页面零配置可用；Go 仍走 HTTP。`security.injectBridge=false` 可关。

## 10. 工具链与部署

```
# 铺运行时（二选一）
go run ./tools/pack      -dist <electron dist> -out D:\Apps\runtime -app ./app
go run ./tools/relruntime -zips <官方 zip 目录> -out D:\Apps\runtime -version v16.0.9

# 出单个产品的发行文件（exe + <程序名>.app.json + 图标，不含运行时）
go run ./tools/build -targets win-x64 -bundle shared -out dist

# 自检：同级 runtime 在不在、版本/端口/GPU
go run ./tools/doctor -dir D://Apps

# 开发态：直接起外壳（业务程序自己 go run .）
go run .
```

> `pack` 吃本机已有 dist 目录；`relruntime` 吃官方跨平台 zip（自动把 `electron(.exe)` 改名为 `gobrowser(.exe)` 并注入 `app.asar`）。
> `tools/build` 另有 `-single`（单文件载荷）、`-iss`（Inno Setup 脚本）、`-runtime-dir`（直接复制现成 runtime）。

| 部署单元 | 内容 | 部署方式 |
|---|---|---|
| 运行时 | 一份 `runtime\` 目录（约 180 MB） | 解压到统一目录，一次 |
| 产品 | `MyApp.exe` + `MyApp.app.json` + 图标（+ 可选自带 `runtime\`） | 拷进同一个统一目录 |

**升级约定**：直接把 `runtime\` 整个替换。Windows 下正在运行的 `gobrowser.exe` 删不掉，
所以升级前必须先退出所有用它的程序（`go run ./tools/doctor -dir <统一目录>` 可先体检一遍）。
如果"升级时要能滚动"变成刚需，再引入 `runtime\1.0.0\` + `current.json` 的多版本结构 —— 现在先不引入。

## 11. 安全

1. 只监听 `127.0.0.1`，端口随机，token 每次启动新生成、不落盘。
2. 控制 API 校验 `Origin` / `Sec-Fetch-Site`，拒绝页面跨域调用（页面走 §9.3 bridge）。
3. 页面默认 `contextIsolation: true` + `nodeIntegration: false` + CSP；白名单外链接交系统浏览器。
4. DevTools 默认关，页面侧不暴露调试入口；生产环境的调试开关只在开发态打开。
5. 统一目录不要求管理员权限（绿色部署），但运行时目录一旦被替换就等于换了整个渲染层 —— 生产环境建议把统一目录设在普通用户无写权限的位置（如 `C://Program Files\` 或 `D://Apps` 并收紧 ACL）。

## 附录 A：Go 侧构建与发布（实测）

### A.1 先分清"嵌入"的两种含义

| 做法 | 体积 | 首次启动 | 升级 | 建议 |
|---|---|---|---|---|
| **A. 真嵌进 exe**（`go:embed` 或尾部追加自解压） | exe ≈ 190 MB | 需把 180 MB 解压到磁盘，1–3 s，且磁盘占双份 | 运行时升级要重编整个 Go 程序 | 仅在"必须单文件分发"时用 |
| **B. 构建期组装**（Go 只出 exe，runtime 目录放进发布目录） | exe ≈ 2 MB | 0（直接就绪） | 换 runtime 目录即可 | **推荐（默认）** |

Go 编译产物实测只有 **1.8–2.2 MB**（因为 UI 由后端 HTTP 提供，不需要把前端打进 exe）——这是本架构的天然优势，A 方案会把它毁掉。

### A.2 两种发布变体（同一份源码，不同组装）

| 变体 | 发布目录内容 | 适用 |
|---|---|---|
| `bundled`（自带） | `MyApp.exe` + `MyApp.app.json` + **`runtime\`** | 客户机器干净、要绿色单目录分发 |
| `shared`（复用） | `MyApp.exe` + `MyApp.app.json` | 与已有 runtime 的程序放在同一目录 |

**变体差异只发生在组装步骤，不需要编译期 tag、不需要代码分叉。**

```
dist\
├── win-x64\
│   ├── ReportCenter.exe         ← Go 交叉编译产物（约 2 MB）
│   ├── ReportCenter.app.json    ← 与 exe 同名
│   └── runtime\              ← 仅 bundled 变体有（约 180 MB）
└── linux-arm64\
    ├── ReportCenter
    ├── ReportCenter.app.json
    └── runtime\
```

### A.3 交叉编译矩阵（本机 Go 1.20.14 实测）

| GOOS/GOARCH | 对应运行时包 | 结果 | 耗时 | 产物 |
|---|---|---|---|---|
| `windows/amd64` | win32-x64 | ✅ | 2.7 s | 1.9 MB |
| `windows/386` | win32-ia32 | ✅ | 12.2 s | 1.9 MB |
| `linux/amd64` | linux-x64 | ✅ | 14.9 s | 1.8 MB |
| `linux/arm64` | linux-arm64 | ✅ | 13.4 s | 1.8 MB |
| `linux/loong64` | linux-loong64 | ✅ | 12.2 s | 1.9 MB |
| `linux/mips64le` | linux-mips64el | ✅ | 11.9 s | 2.1 MB |
| `linux/sw64` | linux-sw64 | ❌ `unsupported GOOS/GOARCH pair` | — | — |

全部用 `CGO_ENABLED=0`，产物纯静态，无 glibc 版本烦恼。

> **红线：申威 sw64 没有官方 Go 支持。**
> 要么用申威提供的移植版 Go 工具链，要么该平台用 gccgo 交叉编译，要么放弃该平台。
> 这是唯一一个"Electron 有包、Go 没支援"的格子。（龙芯 loong64 / mips64el 都 OK。）

### A.4 Windows 的图标与版本信息

Windows 的 exe 资源必须在编译时以 `.syso` 形式链进去（Go 没有运行期改资源的能力）：

```
go install github.com/tc-hib/go-winres@latest
go-winres simply --icon icon.png --product-name "报表中心" --product-version 1.2.0 \
                 --file-version 1.2.0 --company-name "ACME" --product-desc "报表中心"
# 生成 rsrc_windows_amd64.syso / rsrc_windows_386.syso，放回包目录即可
```

- syso **按架构命名**，交叉编译时自动匹配，386 与 amd64 各一份。
- Linux 不需要 syso：程序名 = 文件名，图标靠 `.desktop` + hicolor。
- 版本号务必与 `app.json.version` 一致（构建脚本里做一致性校验，别手工同步）。

### A.5 构建脚本要做的事

```yaml
# targets.yaml
app: { name: 报表中心, appId: com.acme.report, version: 1.2.0 }
targets:
  - { goos: windows, goarch: amd64, runtime: electron-v16.0.9-win32-x64.zip, mode: bundled }
  - { goos: linux,   goarch: arm64, runtime: electron-v16.0.9-linux-arm64.zip, mode: shared  }
```

流程（可并行）：

```
1. 校验：app.json 与 targets.yaml 的版本/appId 一致
2. 生成 syso（windows 目标）
3. GOOS/GOARCH/CGO_ENABLED=0 go build -ldflags "-s -w -X main.version=1.2.0"
4. 组装：mkdir dist/<os>-<arch>，拷 exe + <程序名>.app.json
         mode=bundled 时把对应 runtime zip 解开成 runtime\
5. 校验：runtime 里 gobrowser.exe / electron.sign / lic / resources\app.asar 齐全
6. 压缩：zip / tar.gz（或交给安装包工具）
```

### A.6 "自带 vs 复用"的一个坑

发现顺序是「同级 `..\runtime` 优先，自带 `.\runtime` 兜底」，所以：

> **bundled 版如果被放进一个已有 `..\runtime` 的目录，它会先用别人的运行时。**

三种处理，按简单程度排序：

| 方案 | 做法 | 代价 |
|---|---|---|
| 保持现状 | 接受"外部优先" | 简单，但 bundled 不自包含 |
| 加开关 | `app.json` 加 `"preferBundled": true`，自带版优先 `.\runtime` | 一个字段 + 几行判断 |
| 构建区分 | bundled 版把 runtime 放 `.\runtime` 且默认 `preferBundled` | 最符合直觉，推荐 |

### A.7 握手通道实测（Windows）

Go 用 `exec.Command` + `StdoutPipe` 读一行 JSON：

```
第1行: ""                                                    ← Electron 启动会先吐一个空行
第2行: {"event":"ready","port":61778,"token":"t0k3n-abc",...}  ← 真正的握手
```

- ✅ 管道可用，Go 读得到；**必须跳过空行**，不要假设第一行就是 JSON。
- ❌ 不要用"重定向到临时文件再轮询"（实测读不到，写入时机不可靠）。
- Go 侧还要过滤环境变量 `ELECTRON_RUN_AS_NODE`（继承自 IDE 时会让外壳退化）。

## 附录 B：运行时怎么随程序走（两种形态，均已实现）

| 形态 | 命令 | 产物 | 运行时位置 |
|---|---|---|---|
| 目录 | `build -bundle bundled` | exe + `runtime\` | 程序同级 `runtime\` |
| 复用 | `build -bundle shared` | 只有 exe | 用同级已有的 `runtime\` |
| 单文件 | `build -single` | 一个 exe（≈84 MB） | 首次运行解压到 `%LOCALAPPDATA%\gobrowser\<appId>\runtime-<sha12>` |

**单文件载荷格式**（`internal/payloadfmt`，读写共用一份定义）：

```
[ exe 原始内容 ][ runtime.zip ][ trailer 36B ]
trailer = magic "WSPAYLD1"(8) | version(4) | offset(8) | size(8) | sha256前8字节(8)
```

- 只往文件尾追加，不改 PE 头/段表，也不碰 `electron.sign` 覆盖的 `.text` —— 加固验签不受影响。
- 摘要写进 trailer 与解压目录里的 `.payload`，**换了 exe 就自动重新解压**（等于 runtime 跟着程序版本走）。
- 实测：win-x64 单文件 83.9 MB（载荷 78.4 MB），首次启动 4.55 s（其中解压约 2.1 s），之后 2.46 s。
- 取舍：省掉"runtime 目录不在原位 / 被替换"的部署事故，换来更大的 exe 与首次启动延迟；对杀软更敏感。
